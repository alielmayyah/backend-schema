API versions that cannot change

Installed TVs and phones can't be updated, so every version below keeps its paths, methods, encoding and response shape exactly (PLAN constraint 1). The migration has to keep the device data each version reads byte for byte: if a value changes form, the app on that device stops working. Route lists come from docs/inventory/endpoints-*.md; the "how it finds the device" column is from the old controllers.

Version locks

Each backend records the newest API a device has used and then refuses older ones, so an attacker can't fall back to a weaker protocol. The three do it differently, and old apps depend on the exact behaviour.

Decisions already made

  1. Two device collections. pendingDevices holds unpaid devices and is never cleaned; devices holds paid devices only. Paying is the only way in.Spec 2026-10-19 and mongo-device.repository.ts. Supersedes ARCHITECTURE §7 (one collection with a state field) and PLAN §6 (30-day TTL and trialHistory).
  2. Migrated devices keep their old id. _id becomes the old ObjectId as a 24-character string. New devices get UUIDs.The V4 routes compare the device id inside the app's XOR token with _id (get-v4-device-info.use-case.ts). A new id would log out every installed app.
  3. One device per MAC per brand, whatever the app type, checked across both collections. MACs are normalized to lowercase with colons.PLAN §5.3, index migration 0001-devices-indexes.
  4. Duplicate MACs are merged into a survivor with the best licence; playlists move to it, and losers' ids are listed in legacy.mergedFrom[]. Two paid records with different expiries go to manual review.PLAN §5.3.
  5. Indexes come from migrations only (pnpm cli migrate:tenants), never Mongoose autoIndex. Planned: unique macAddress and deviceKey, partial unique appDeviceId, 5-minute captcha TTL.devices.migrations.ts.
  6. Per-brand settings live in one tenantConfig document (_id: "tenant"). Keys: devices.trialDays and legacy.profile (ibo | bob | cr), which each migrated brand gets from the backend it came from.mongo-device-settings.ts.
  7. Every migrated row carries legacy: {source, id} and the ETL is re-runnable: a second run changes nothing.PLAN §5, M12.

Open questions

  1. is_trial meanings: answered from the code. See "Where each old device lands": the side is decided by evidence of payment, not by the number alone. Needs sign-off on the proposed rows.
  2. MAC-switch, recovery and transfer losers. Proposed: pendingDevices as an expired trial with the switch recorded. Alternative: devices with license.status = revoked. Product owner's call.
  3. Old u_id has two meanings. The same field holds the V4 6-character u_id and the v2/v3 install uid. Proposed: a 6-character value on a device at apiGeneration 4 → uid; anything else → appUid; the raw value always in legacy.uId.
  4. cr uppercase 'V4'. Old cr only locks lowercase 'v4' devices out of the legacy TV route. Mapping both to generation 4 locks the uppercase ones too: stricter than today. Keep the stricter rule?
  5. Tokens of merged duplicates. A V4 app holding a loser's token fails the _id check after the merge. Look the id up in legacy.mergedFrom, or let those apps log in again.
  6. Shared fallback MACs (52:54:00:12:34:56/57/59). Old data has one row for many TVs; it cannot be split. Proposed: migrate it under its app_device_id if present, otherwise report it and skip.
  7. playlists.deviceId type: string. Device ids are strings in the new code; PLAN §5.2's ObjectId is outdated.
  8. Passwords: copy the hashes. Admins, resellers and customers use bcrypt in all three backends, so passwordHash is copied unchanged and nobody has to reset.
  9. bob app_purchase rows have no device by a bug: saveAppPurchase reads the pending promise instead of the device, so device_id and price are always empty, while the device itself was set to lifetime by MAC. The transactions cannot be linked; migrate them unlinked and flagged.
  10. activatedAt for migrated paid devices. No old field holds it. Proposed: the earliest paid transaction, code or coupon use, else the migration time with a flag.
  11. No ibo sample database. ibo mappings come from code only and need a production copy to check.
  12. Tenants not to migrate: cr's bob is local-test only; mac, macplayer, duplex, 0player and king appear in code but were never configured.
